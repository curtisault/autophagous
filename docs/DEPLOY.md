# DEPLOY

How AUTOPHAGOUS ships. Deploy target is **Cloudflare Pages**, project
name **`autophagous`**, live at `autophagous.pages.dev` plus any custom
domain attached later.

## Pull requests

Every pull request runs `.github/workflows/test.yml`, which is the same
suite the deploy gates on — the mise toolchain, `deno install`,
`deno task test` — and nothing else. It exists so a failing test is
visible on the branch rather than on `main` after the fact.

`deno install` is kept here even though the test runner does not need
`node_modules`: it is what makes a broken `deno.json` or `deno.lock`
fail on the PR instead of surfacing later at the deploy build.

Deliberately **not** on `push`: `deploy.yml` already runs the suite for
`main`, so a push trigger here would double every run for no extra
signal. Superseded runs on the same PR are cancelled
(`concurrency.cancel-in-progress`), and the job asks for
`contents: read` and nothing more.

It does not build or assert the 404 contract — those live in the deploy
job, where they gate the thing they protect. If a PR needs to prove the
build too, add the steps here rather than moving them.

## The pipeline

Every push to `main` runs `.github/workflows/deploy.yml`:

0. **Cache mise tools** — restored *before* mise-action. `elm-test-rs`
   is installed from a git fork via the cargo backend, so it compiles
   from source; without this cache every run pays ~40 s plus the
   dependency crates. Keyed on `mise.toml`.
1. `jdx/mise-action@v2` — installs the whole toolchain (deno, elm,
   elm-test-rs, typst) from `mise.toml`. That file is the single
   source of truth for every tool version, locally and in CI. **No
   node is installed at any point.**
2. `deno install` — for the build. Neither the Elm compiler nor the
   test runner comes from `node_modules`.
3. `deno task test` — **This is a gate:** a failing route test blocks
   the deploy (the runner exits non-zero; verified). Add further gates
   here as the project grows.
4. `deno task build` — Vite production build to `dist/`, with Deno as
   the runtime. Output is byte-identical to what Node produced before
   the migration.
5. **Assert the SPA fallback stays off** — fails the build if
   `dist/404.html` is missing or if a wildcard rule appears in
   `_redirects`. Both would silently reinstate the failure described
   under *The 404 contract* below.
6. `wrangler pages deploy dist --project-name=autophagous` via
   `cloudflare/wrangler-action`
7. Zone cache purge — self-skips until `CLOUDFLARE_ZONE_ID` exists

Step 6 is the one place Node still executes, inside
`cloudflare/wrangler-action` — that is the action's own
implementation, not this project's toolchain. `deno task deploy` does
the same work under Deno if you would rather not have it at all; the
action is kept because it is the battle-tested path for the one step
CI cannot rehearse.

Elm package downloads are cached on a key derived from `elm.json`,
Deno's module cache on one derived from `deno.lock`, and the mise
tool directory on one derived from `mise.toml`.

There is **no** Cloudflare Git integration — do not "Connect to Git" in
the Cloudflare dashboard. The GitHub Action is the only build pipeline;
the dashboard integration would create a second, competing one.

## The 404 contract

**Do not delete `public/404.html`.** Its presence is what turns
Cloudflare Pages' SPA fallback *off*.

With the fallback on, a request for a hashed asset that no longer
exists (a stale tab after a deploy) is answered with `index.html` as
`200 text/html`. Strict MIME checking refuses that, the page renders
unstyled — and because `/assets/*` carries a one-year `immutable`
header, the mistyped response is cached under that URL for a year, in
the browser *and* in edge caches you cannot see from one machine.

This is documented Cloudflare Pages behaviour, not a hypothetical: the
SPA fallback is on by default and off only while a `404.html` exists.

Client routes still work, because `public/_redirects` rewrites them to
`/index.html` **by name**. Never widen that to `/* /index.html 200` — a
wildcard reinstates the failure. A new route means a new line, in both
`src/Route.elm` and `_redirects`. The CI guard enforces both halves.

## Cache policy

`public/_headers`. The rule: a URL may be cached immutably only if its
content can never change under that name.

| Path | Policy | Why |
|---|---|---|
| `/assets/*` | 1 year, immutable | Vite hashes these |
| `/fonts/*` | 1 year, immutable | Not hashed but content-stable — replace a face by shipping a *new filename*, never by overwriting |
| `/downloads/*` | 1 hour, revalidate | `cycle-log.pdf` is regenerated by `deno task print` under the same name; immutable here would pin readers to a superseded printable for a year |
| `/`, `/index.html`, `/404.html` | no-store-ish | HTML is the entry point to hashed assets and must never outlive a deploy |

## Configuration knobs

| Knob | Where | Constraint |
|------|-------|-----------|
| Trigger | `on.push.branches` | `main` only |
| Every tool version | `mise.toml` | The single source of truth — CI reads the same file. Bump there and build locally first |
| Elm version | `mise.toml` | Stay on the **0.19.1** line — `elm.json` declares it |
| Test runner | `mise.toml` | `elm-test-rs` on the **3.x** line — it is what supports `elm-explorations/test` 2.x. Pinned to a **fork** for Deno 2 support; drop back to `ubi:mpizenberg/elm-test-rs` once upstream ships the fix |
| JS runtime | `mise.toml` | Deno, and only Deno. Do not add node back — if something will not run under Deno, fix that instead |
| Dependencies | `deno.json` | `imports`, with `deno.lock` committed |
| npm `overrides` | `package.json` | The **only** thing that file is for — `deno.json` cannot force a transitive version. Deno reads it. Without it, `cross-spawn` resolves to the vulnerable 6.0.5. Never add dependencies or scripts there |
| Project name | deploy step, `wrangler.toml` `name`, `deno.json` `deploy` task | All three must say `autophagous` |
| Secrets | deploy step | Names must match the repo secrets exactly |
| Zone purge | `Purge zone cache` step | Activates when `CLOUDFLARE_ZONE_ID` is a repo secret AND the token has *Zone → Cache Purge → Purge*. Self-skips until then |
| Gates | the `deno task test` and assert steps | Never remove; add further gates as steps *above* the deploy |

Manual re-run: repo → Actions → the failed run → Re-run all jobs. To
trigger without a push, add `workflow_dispatch:` under `on:`.

## One-time setup

### Cloudflare

1. **API token:** dash.cloudflare.com → avatar → My Profile → API
   Tokens → Create Token → template **"Cloudflare Pages — Edit"** (or a
   custom token with *Account → Cloudflare Pages → Edit*). Copy it
   immediately — it is shown once.
2. **Account ID:** right sidebar of the dashboard account home, or
   `deno run -A npm:wrangler whoami`.
3. **Zone ID** (optional, for the deploy-time purge): dashboard → the
   zone → Overview, right sidebar. Add as `CLOUDFLARE_ZONE_ID`, and
   edit the token to also grant *Zone → Cache Purge → Purge*.

The Pages project is **not** created in the dashboard — the first
`wrangler pages deploy` (CI or local) creates `autophagous`.

### GitHub

Repo → Settings → Secrets and variables → Actions → New repository
secret, twice (exact names):

| Secret | Value |
|--------|-------|
| `CLOUDFLARE_API_TOKEN` | the token above |
| `CLOUDFLARE_ACCOUNT_ID` | the account ID above |

### Custom domain

After the first successful deploy: Workers & Pages → **autophagous** →
Custom domains → Set up a custom domain.

- DNS already on Cloudflare: one click; CNAME and cert are automatic.
- DNS elsewhere: CNAME to `autophagous.pages.dev`. Apex domains
  generally cannot CNAME at external hosts — move nameservers to
  Cloudflare if that bites.
- **Attach every hostname you intend to serve, separately.** A
  subdomain with proxied DNS but no Pages attachment has no edge route
  and returns HTTP 525 for the page *and* every asset. The apex being
  healthy tells you nothing about `www` — each hostname is routed
  separately.

`autophagous.pages.dev` keeps working alongside any custom domain.

## Manual deploy

One-off from a workstation (first time:
`deno run -A npm:wrangler login`):

```
deno task deploy
```

Builds and pushes `dist/` to the same project. It does **not** run the
test gate or the 404 assertion — prefer pushing to `main`.

## Troubleshooting

- **CI fails at `deno task test` / build with "elm not found":** the
  `jdx/mise-action` step was removed, or `elm` was dropped from
  `mise.toml`. Nothing else puts the compiler on PATH — it is not a
  dependency of anything.
- **`deno task test` fails with "Deno.read is not a function":** the
  `elm-test-rs` pin fell back to upstream (`ubi:mpizenberg/…`).
  Upstream's Deno support predates Deno 2. Use the fork pinned in
  `mise.toml` until the fix ships upstream.
- **"command not found" locally:** run `mise install`. The runner and
  compiler come from `mise.toml`, not from `deno install`.
- **CI suddenly spends minutes compiling Rust:** the *Cache mise
  tools* step was removed or its key changed. `elm-test-rs` builds
  from source; that cache is what hides the cost.
- **CI fails at "Assert the SPA fallback stays off":** someone deleted
  `public/404.html` or added a wildcard to `_redirects`. Read *The 404
  contract* before overriding — the guard is the point.
- **Deploy step 401/403:** token expired or missing Pages Edit; re-issue
  and update the GitHub secret.
- **Deploy created a second project:** `--project-name` drifted out of
  step with `wrangler.toml` / `deno.json`.
- **Site deployed but domain 404s:** custom domain not attached, or DNS
  still pointing elsewhere.
- **HTTP 525 on one hostname, page and assets alike:** that hostname has
  proxied DNS but was never attached to the Pages project. A routing
  failure — no amount of cache-clearing or redeploying fixes it.
- **Unstyled page + "Refused to apply style … MIME type ('text/html')":**
  the 404 contract was broken; see above. If a private/incognito tab is
  *also* broken, the poisoned copy is not on the device — it is in an
  intermediary (an edge colo, a VPN/proxy cache). Fix: zone → Caching →
  Configuration → **Purge Everything**, which is safe for a static site
  and is what the workflow's purge step automates. Edge caches are
  per-location, so a `curl` from one place proving the site healthy does
  **not** rule this out for a device elsewhere.
- **Mobile styles silently not applied (desktop layout at phone width)
  while desktop responsive testing looks fine:** the CSS minifier
  rewrote `@media (max-width: …)` into range syntax that pre-16.4 iOS
  WebKit cannot parse. `build.cssTarget` in `vite.config.js` pins
  against this; after any Vite major bump verify with
  `grep -o "@media[^{]*" dist/assets/*.css` that queries still say
  `max-width`, not `width<=`.
